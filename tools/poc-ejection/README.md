# `tools/poc-ejection/` — ejection, both modes (#3408, plan item 3)

```sh
npx tsx tools/poc-ejection/eject.ts --mode package        # every package from `npm pack` tarballs (Q84 A)
npx tsx tools/poc-ejection/eject.ts --mode source         # the component source copied in; the tokens stay a tarball
npx tsx tools/poc-ejection/eject.ts --mode <m> --keep     # leave the client in $TMPDIR and print where
npx tsx tools/poc-ejection/eject.ts --mode <m> --plant file-link|engine-import|repo-url|multiline-import   # a planted leak
npx tsx tools/poc-ejection/eject.ts --self-test           # the counter and the summary line, on planted fixtures
```

Each run builds a standalone client in `$TMPDIR`, outside the repo. The client has the brand's token CSS and all
three POC components (button, text field and password field), each in both forms: plain HTML/CSS and the custom
element. The page is `client/index.html`, and the entry is `client/main.<mode>.js`. The run then checks three things:
- **It builds clean:** esbuild exits 0 and prints no warning.
- **Its bundle reads only the client:** the build writes esbuild's metafile, and every input esbuild resolved must lie
  inside the client folder. Otherwise the run fails with "the bundle reads N files outside the client: …". This check
  reads what the bundler resolved, so it doesn't depend on the counter's patterns. A multi-line import, a `tsconfig`
  path or an alias into the repo shows here (#4471 M1). A `new URL('…', import.meta.url)` doesn't: esbuild doesn't
  read it as an input, so the counter alone catches it, on one line or with its string on the next (#4471 S1).
- **It renders, in Chromium, from disk:**
  - no script error;
  - every element is defined and renders its markup;
  - the plain password field's script runs;
  - the filled HTML button has a solid token fill, and its background, height and radius equal the element's.

**Source mode** runs `copy-source.mjs`, the copy script a client would run. It copies each component package's
published files, less the README, into `src/prism3/`. Then it installs what the copies need (Lit). It changes one
thing (owner decision 3 on #4471): a file that opens with a "GENERATED by packages/…" header gets a provenance line in
its place, naming the package and version it was copied from. The header runs through its "do not edit; … regenerate"
line. Everything else is copied byte for byte, so the counter still measures what the copies say about prism3.

**What it measures, per mode:**
- **Steps:** each command the client runs or file it writes by hand, in order.
- **Wall-clock seconds:** from the first step to a built client. The render check is timed separately.
- **Two counts of references left to prism3** (`refs.ts`):
  - **(a) references back into the repo or workspace.** Each is named by kind: a `file:` or `link:` into the
    repo, a `workspace:` link, an import of a `@prism3` package the client wasn't given, a path that resolves into the
    repo, the repo's absolute path, a path that names a file in the repo, or the repo's URL.
  - **(b) `@prism3/*` package names.**
- **How an upstream change arrives,** for each piece: by a package version, by the version the copies carry (the
  provenance line), or by no channel. This is a measurement only, until #3411 is built.

**Scored count: owner decision D1, answered A (2026-11-23).** The run scores count (a), with a target of 0. Count (b)
is the delivery, not a leak, so it's reported and not scored. The choice is `SCORED` in `eject.ts`.

**What it scans:** every file the client owns. That's everything under the client folder except `node_modules/` and
`dist/`, so in source mode it includes the copies. References in the installed `node_modules/@prism3/` files are
printed on their own line and never added to (a).

**It exits 1 on:** a failed step, a build warning, a bundle input outside the client, a failed render check, or a
scored count above 0. A failed step quotes esbuild's first `✘ [ERROR]` line, else npm's first `npm error` line. The scorecard
then reads FAIL with this tool's line, never a count. The rows are `eject-package` and `eject-source` in
`tools/poc-scorecard/measures.ts`. It needs the npm registry for Lit and esbuild (a warm npm cache serves them) and
Chromium.

**Independence (`docs/34`):** the counter never reads the copy script, the install output or the step list. It knows
the repo from the repo: its root, its folders and files, its workspace names and its URL. The packages each mode
delivers are written down in `eject.ts`. The self-test plants each kind of reference into a clean fixture, and each
must count exactly 1, by that kind. So must each specifier form the line patterns once missed: a multi-line
`import {…} from` or `export {…} from`, into the repo or from `@prism3/engine`, and a relative `new URL(…)`, on one
line or with its string on the next. One more case runs the real copy script: each copy whose source opens with a
generated header must open with `<package>@<version>`, and its header must name no repo path, by the counter. The rest
of the file must be byte for byte its source. The case finds those files from the sources, not from the copy script. `--plant`
does the same to a real run, which must FAIL by kind. `--plant multiline-import` goes in before the build, so the
metafile check fails it by name first.
